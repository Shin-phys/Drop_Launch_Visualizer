# 投射運動を観る

高校物理の授業用の教材アプリです。動画はブラウザの中だけで処理され、どこにも送信されません。

- **① 斜方投射を観る** … 水平方向が等速であること、最高点をはさんで上りと下りが時間反転で対称であることを確かめる
- **② 自由落下とくらべる** … 斜方投射の最高点と自由落下の落下開始をそろえて同期再生し、落下距離が一致することを確かめる

①のまとめから「②に引き継ぐ」を押すと、動画と最高点がそのまま②の右側（開始点＝最高点）に渡ります。

## PC とスマホ

同じ1つのアプリが、画面の幅で外枠を切り替えます（`body.compact`）。中身のロジックは共通で、変わるのは並べ方と進め方だけです。

- **PC（広い画面）** … タブを横に並べ、好きな順に行き来できます。キーボード操作（<kbd>←</kbd><kbd>→</kbd> でコマ送り、<kbd>Shift</kbd>で10コマ、<kbd>Space</kbd>で再生）とドラッグ&ドロップが使えます。
- **スマホ（760px 以下）** … 画面を縦に固定し、上から「映像 → 操作バー → 説明」の順に置いて、下部で1ステップずつ進めます。映像の高さは画面の34%以上を確保しています。読み込みカードは動画が入ると1行に畳まれ、「動画を変える」で開き直せます。

ヘッダー右の「スマホ表示 / PC表示」ボタンで手動でも切り替えられます（PCで生徒の見え方を確認するとき用）。一度押すと画面幅による自動切り替えより優先されます。

どちらでも使える操作:

- **拡大** … PCは操作バーの 🔍−／🔍＋／⤢、スマホはパネル右上のボタン（1× → 2× → 3× → 1×）と2本指のつまみ。拡大中は映像を指でなぞると表示位置が動きます。映像とオーバーレイ（線・点）を一緒に拡大しているので、拡大したまま位置をクリックしてもずれません。
- **コマ送りボタンの長押し** … 押しっぱなしで連続して送れます（0.4秒後から約11コマ/秒）。
- **ボタンは指を離したときに効きます**（`A.attachRepeat`）。押した瞬間ではありません。スマホで画面をスクロールしようとして、たまたまボタンの上に指を置いただけで値が動いてしまうためです。10px 以上動かしたらタップではなくスクロールとみなして、何も起きません。

スマホ側で意図的に変えていること:

- コマ送りは**映像の上を横になぞる**操作にまとめ、ジョグ帯は出しません（縦を節約するため）
- 再生速度は4つ並んだボタンではなく、押すたびに一巡する1つのボタンにします
- ⏮先頭・±10コマのボタンとキーボードの説明は隠します
- 縦動画でも左右2列を維持します（縦長の映像は横に並べたほうが大きく見えるため）

## 撮影のしかた

**スマホは横向きに固定し、斜方投射と自由落下を続けて1本の動画に撮ります。** カメラは遠くに置いてズーム、明るい場所で。

**コマ数は「その端末で安定して撮れる最大」を選びます。**「240fps にすれば良い」ではありません。端末によっては、高いコマ数を選ぶと
（1）コマの間隔が不揃いになる（可変フレームレート）か、（2）実際には撮れていないコマを同じ画で水増しします。
どちらでも**1コマ送りあたりの移動距離がまちまち**になり、いちばん見せたい「水平は等速」が壊れます。
**授業前に `check.html` で確かめてください。** 迷ったら、明るい場所での **60fps** がいちばん外れません（高さ1mの落下 0.45秒に27コマ入り、観察には十分です）。

- **なぜ横向きか**：①はボールが画面を横切る運動なので、縦長だと軌道が収まりません。表示のうえでも、スマホを縦に持って見るとき横長動画は映像の枠が 370×208 px になるのに対し、縦長動画は 132×235 px にしかなりません（横幅が3分の1）。②の鉛直運動は「画面の切り取り」で縦長に切り出せるので、横長で撮っておけば両方に使えます。
- **なぜ遠くからズームか**：近くから広角で撮ると、手前と奥で見かけの大きさと速さが変わります。遠くからズームすると差が小さくなり、「まっすぐ横から見た運動」に近づきます。
- **なぜコマ数を上げるか**：ズームで大きく写すぶん画面内の動きが速くなるので、コマ数と露光の短さが効きます。高さ 1 m の落下は 0.45 秒しかなく、30fps では14コマしか写りません。ただし**安定して撮れる範囲で**上げること（上の注意）。
- **なぜ明るい場所か**：高速撮影は1コマあたりの露光時間が短いので、暗いと端末がコマ数を落としたり同じ画で水増ししたりします。ブレも減ります。
- **なぜ1本に続けて撮るか**：カメラ位置も倍率も同じになるので、②でスケールのずれが原理的に起きません。①のまとめから「② に引き継ぐ」でそのまま渡せます。

## ①「水平：等速か？」の進め方

画面の文言は短く、**結論を先に言わない**方針です。「〜です」ではなく「〜に見えますか」。長い説明は `<details>` に畳んであります。タブに入った時点で**カメラと背景隠しが有効**になっています。

1. **帯を置く** … ボールをタップして基準の帯を合わせる。幅はボールの大きさくらいに。
2. **ちょうど良いカメラ速度を探す** … 速さを変えて再生 → 一時停止 → **⏮ 先頭** でやり直し。物体が帯の中に収まり続ける速さを探します。
3. **Δt ずつ進めて確かめる** … Δt を決め、縦線を出して「Δt すすむ」で1押しずつ進める。
4. **ストロボにする** … 通り過ぎた位置が1つずつ残っていく。押す前に「次はどこ？」と聞く。
5. **鉛直も見る（横線）** … 最高点を 0 として 1, 4, 9, 16 の位置に線を引く。あいだの距離が 1 : 3 : 5 : 7 になる。

**カメラの速さの刻みは ±0.05／±0.005／±0.001 の3段階**（長押しで連続）。スライダーは粗いので、詰めるときは下2段か数値入力を使います。

**速さの数値は、カメラを合わせた値そのものを使います。** 以前あった「ボールを2点タップして測る」手順は廃止しました。タップの位置誤差が Δt あたりの変位に対して大きすぎるためです ─ Δx が画面幅の 8%、タップ誤差が 1% だとすると、2点法の誤差は **25%** に達します。いっぽうカメラ合わせは飛行の全区間（1〜2秒）に対する当てはめなので、帯の幅 6%・飛行 2 秒なら誤差は 0.03 画面幅/秒 以下、v=0.4 に対して **7% 程度**。**長い区間に当てはめるほうが精度が高い**というだけのことです。

**速さの指定は3通り**：スライダー（粗く）、±0.005／±0.05 のボタン（長押しで連続）、数値の直接入力。スマホではスライダーの1ピクセルが 0.02 相当になるため、細かい値はボタンか数値入力で決めます。

**縦線の間隔**は「カメラの速さ × Δt」。画面には「この速さなら Δt のあいだに 画面幅の 8.0%」と出ます。**「Δt すすむ」が要る理由**：ふつうに再生すると Δt ごとの位置は目で追えません。

**タップして位置を取るあいだは、カメラのパンとマスクが自動で止まります。** 止めないとボールが帯の外に隠れて選べません。

**基準の帯の初期値**は 幅 6%／帯の外を隠す 75%／中央の線 50%／帯の塗り 0%。位置はスライダー・タップ・ドラッグの3通りで合わせられます。

**帯まわりには線が3本見えますが、出どころは2つです。** 中央の線1本は「中央の線」、帯の**ふち**の線2本は「帯の外を隠す」が作る明るさの境目です。帯の幅が 6% だと、スマホでは帯そのものが太い線に見えるため、「中央の線を 0% にしたのに線が残る」と受け取られます。ふちを消すには「帯の外を隠す」を 0% にします。スライダーの名前は、効く先を名乗るように付けています（`外の濃さ` → `帯の外を隠す`、`線の濃さ` → `中央の線`、`帯の色` → `帯の塗り`）。

**背景を隠す**のは、追いかけカメラ中の認知の問題への対処です。視覚系は画面の大部分を占めて動くものを静止した基準として採用してしまうため、背景が流れるとボールが逆向きに動いて見えます（誘導運動）。情報を消す操作なので、**「カメラ → 0.400 画面幅/秒」のバッジ**を必ず出しています。**「もとの映像と並べる」**は同じ運動を2つの見方で同時に見せる方法です。

## ストロボと横線

### なぜ一括生成ではなく、1つずつ増やすのか

完成したストロボ画像を先に見せるのは、**答えを配ってから問いを出す**ことです。1押しで1つずつ増えるなら「次はどこに出る？」と聞けます。認識の課題が予測の課題に変わります。教師の説明なしで進める方針とも、そのまま噛み合います。

実装も一括より軽くなります。裏で動画をもう1つ開いて全コマを取りに行く処理が要らず、**「Δt すすむ」を押した時点ですでに画面に出ているコマ**を1枚足すだけで済みます。

### 蓄積するのは「過去の位置」だけ

`O.shots` に入るのは**もう通り過ぎた位置**のコマだけです。いまの位置は生の映像がそのまま受け持ちます。こうしておくと：

- ストロボ中でも、ふつうのコマ送りで画がちゃんと動く（合成画が映像を覆い隠してしまわない）
- 「Δt すすむ」＝ いま居る位置を置いてから進む、「Δt もどる」＝ 戻ってから最後の1つを消す、と対応がきれいになる

毎コマの描画は **①生の映像を下地に描く → ②過去ぶんを焼き付けた板（`trail`）を明暗くらべで1回載せる** の2回だけです。溜まった枚数によらず一定なので、スマホでも重くなりません。`trail` は足すときだけ差分更新し、消すときだけ作り直します（`lighten` は引き算ができないため）。

### 球の位置は推定しない

合成は `globalCompositeOperation` の `lighten` / `darken`、つまり**素の画素どうしの明暗くらべ**だけで行います。球を検出して小窓を貼る方式は採っていません。それをやると「等間隔に見えた」のがアプリの仮定のせいなのか映像のせいなのか区別できなくなり、**いま確かめようとしていることの証拠にならなくなる**からです。

同じ理由で、**ストロボ中は追いかけカメラを切ります**。追いかけカメラは水平の動きを打ち消す機能なので、水平の動きを見る道具と同時には使えません（`obGrid`／`obStrobe`／`obCam` は互いに排他）。

### 半端な Δt では止めない

「おわり」の手前で残りが Δt に満たないとき、ストロボ中は**進みません**。切り詰めて止めると、最後の1つだけが Δt の格子から外れた位置に出てしまい、等間隔かどうかを見る絵が壊れます。Δt を変えたときとタブを移ったときも、溜めた分は捨てます（別の刻みの絵が混ざらないように）。

### 横線 ─ 位置は 1, 4, 9, 16／あいだは 1, 3, 5, 7

**この2つは別物なので、札の置き場所で分けています。**

- **線の位置**＝最高点からの落下距離。Δt を1単位として **0, 1, 4, 9, 16, 25（= k²）**。札は**右**（`.hline.rule .tag`）。
- **線と線のあいだの距離**＝ **1, 3, 5, 7, 9**。`k² − (k−1)² = 2k−1` なので必ず奇数になります。**こちらには札を置かず**、目盛りを数えて読みます（下記）。両方に数字を出すと、近い場所に似た数列が2つ並んで取り違えのもとになるためです。

### 目盛り ─ 数字の根拠

数字だけだと信じるしかないので、**右の数字のすぐ左に、1単位ずつ刻んだ目盛りを1本通しています**（`.posruler`）。最高点から `k=25` まで、刻みの幅は `O.hlU` で**どこでも同じ**。**5つおきを長く**してあるので、16 や 25 を1本ずつ数えずに済みます。

1本で両方の数字を支えるのが狙いです。

- 上から刻みを数える → **線の位置**（1, 4, 9, 16, 25）
- 線と線のあいだの刻みを数える → **あいだの距離**（1, 3, 5, 7, 9）

区間ごとに目盛りを分けると「どの区間の話か」は分かりやすくなりますが、区間をまたいで数えられなくなり、位置のほうの根拠になりません。通しの1本にしてあるのはそのためです。

**1単位が 5px 未満につぶれるときは、5つおきの長い刻みだけ残します**（数えられない目盛りは、あってもうるさいだけなので）。拡大（ピンチ）は `.vp` ごとかかるので、刻みも一緒に大きくなります。

同じ「1, 4, 9, 16」「1, 3, 5, 7」という数字の並びが近くに出るので、位置を表す線に間隔の数字を貼ると読み違えます（実装当初それをやって取り違えを招きました）。**位置は右・あいだは左**で統一しています。②の「目盛り」（`C.ruler`）も位置で `0（開始点）, 1, 4, 9, 16` と振ってあり、そちらと同じ振り方です。

間隔が広がること自体は印象で言えますが、その広がり方が**数えられる整数**になっているところが効きます。水平が 1, 1, 1, 1 … の等間隔なのと同じ絵の中で見くらべられます。

UI は縦線と同じ形にしてあります ─ **1単位を決めたら、その先は予測**。動かせるのは `k=0`（最高点）と `k=1`（Δt あとの高さ）の2本だけで、`k=4,9,16,25` は `pointer-events:none` にしてあります。予測の線を手で動かせてしまうと、確かめる意味がなくなるためです。

**「最高点にそろえる」ボタン**が要る理由：1 : 3 : 5 : 7 は「最高点から Δt ごと」に数えたときの並びなので、途中の適当なコマから始めれば当然合いません。押すと最高点のコマへ移動し、溜めた分を消します。

②の「目盛り」（`C.ruler`、`[0,1,4,9,16]`）と同じ考え方・同じ CSS クラス（`.hline.rule`）を使っています。

### 画像で保存

`toBlob()` で PNG に書き出します。合成画だけでなく**縦線・横線・ラベル・Δt の値も焼き込みます**。ワークシートに貼ったときに、何を見た絵なのかが残るようにするためです。線の座標は画面の割合そのままで描けます（`A.fitPanels` が映像と同じ縦横比に枠を合わせているので、枠の割合＝映像の割合）。

### ストロボ用キャンバス

`A.strobeCv(p)` が `.vp` の中、映像と `.ovl` のあいだ（`z-index:2`）に作ります。映像と**同じ縦横比・同じ `object-fit:contain`** なので画面上の位置がぴったり一致し、`A.applyTransform` が**映像と同じ変形をキャンバスにも当てます**。拡大（`A.applyView`）は `.vp` ごとかかるので、そちらは何もしなくてもそろいます。

## ②「鉛直：時間反転か？」の折り返し合わせ

ミラー再生は、下りを `最高点 + s`、上りを `最高点 − s` で流します。**コマ送りは両方を同時に動かすので、ふたつのずれは2コマずつしか変わりません。**
最高点の指定が1コマずれていると、それを打ち消す手段がなくなります。そこで「折り返しを1コマ単位で合わせる」の **−1コマ／＋1コマ** は
**逆再生側だけ**を動かします（`O.mirAdj`）。ここだけで奇数コマのずれに届きます。JSONにも保存されます。

## 「コマ数／秒」は選ばせない

ヘッダーの数値が指すのは、**ファイルに実際に入っているコマ数**です。カメラの撮影設定ではありません。ここが食い違います。

**240fps のスロー撮影は、たいてい 60（または 30）コマ/秒のファイルとして保存されます。** 240コマで撮った映像を引き伸ばして、ゆっくり再生されるようにしたものだからです。ファイルの中身は 60 コマ/秒。ここを 240 にすると、1回押しても 1/240 秒しか進まないので、**4回押してやっと1コマ**になります。

やっかいなのは、**小さすぎる値を入れても一見うまくいく**ことです。60 コマ/秒のファイルに 30 を指定すると、1回押すごとに画は変わります。ただし**1コマ飛ばしで進んでいる**だけで、コマ送りの半分が見えていません。「押せば画が変わる」は、正しい値である証拠になりません。

そこで、**選ばせるのをやめました**。動画を読み込むと、見えないところで同じ動画をもう1つ開き、`currentTime` を細かく指定して `requestVideoFrameCallback` が返す `mediaTime`（実際に出たコマの時刻）を拾い、コマの間隔の中央値から実測します。結果は自動で設定され、「この動画は 60 コマ/秒でした」と出ます。選択欄は残してあるので、上書きもできます。

- **本体のプレーヤーでは測りません。** 本体を使うと、測っているあいだ操作が効かず、画面も飛び回ります。別の隠し `<video>` に同じ blob URL を渡して測っています。
- **再生して測ってもいけません。** 画面の書き換えは 60Hz なので、120fps の動画は半分のコマが表示されず、30fps の動画は同じコマが2回表示されます。動画ではなく画面の性質を測ることになります。
- コマの間隔が不揃いなら、その場で警告を出します。
- ②で左右の動画のコマ数が違えば、そう言います。

**スロー撮影のファイルでは、表示される「秒」はファイル上の秒です。** 240コマ/秒で撮って 60コマ/秒で保存された動画なら、実時間は表示の 1/4 です。等速かどうか・上りと下りが対称か・落下距離が一致するか — この教材が見せるものはすべて**比**なので、これらは影響を受けません。効くのは「Δt が何秒か」を数値で言うときだけです。

## コマ落ちチェッカー

`check.html`。動画を選ぶと、**再生せずに 1コマずつ取り出して**次を出します。

- 実際のコマ数／秒（撮影時の設定と食い違っていれば、そう言います）
- コマ間隔の中央値・最短〜最長・ずれているコマの割合
- 前のコマと同じ画（重複）の割合
- ◎ 使える／△ 間隔が不揃い（VFR）／× 同じ画が多すぎる の判定と、撮り直しの指示

**再生して測ってはいけません。** 画面の書き換えは 60Hz なので、120fps の動画を再生すると半分のコマが表示されず、
30fps の動画では同じコマが2回表示されます。**動画の性質ではなく画面の性質を測ってしまう**ので、
`currentTime` を指定して `requestVideoFrameCallback` が返す `mediaTime`（実際に出たコマの時刻）を読む方式にしています。

## 作りの約束ごと

- **ES モジュール（`import` / `export`）は使いません。** `file://` で開いたときに CORS でブロックされ、ダウンロードして開いた生徒の画面が真っ白になるためです。従来の `<script>` タグなら `file://` でも読み込めます。
- **時刻を指定するときは、コマの中央（`A.FT(f)`）を狙ってください。** 境界ちょうど（`f/fps`）を指定すると、動画側の時刻がミリ秒に丸められている分だけ手前のコマに落ち、1回押しても画が変わらないことがあります。区間タブと②のシークバーで実際に起きました。
- **コマ番号は `App.TF()` / `App.FT()` を使ってください。** 動画側が返す時刻は「コマ境界」の場合と「コマ中央」の場合があり、webm などはミリ秒に丸められます。素朴に `Math.floor(t*fps)` とすると1コマずれます。
- **2つの動画を `play()` で同時再生しません。** 必ずずれるので、共通の仮想時計をひとつ持ち、毎フレーム `currentTime` を代入して合わせています（`00-core.js` の `frame()`）。
- **ボタンを `pointerdown` で発火させません。** 発火は `pointerup`（＝指を離したとき）、長押しは「420ms 動かさずに待てたら」。`pointerdown` で即発火し、そこで `preventDefault()` すると、(1) 指を置いただけで値が変わり、(2) その場所からページをスクロールできなくなります。実際に「カメラ速度が勝手に 0.05 増える」不具合になりました。
- **シーク中に来た指示を捨てません。** `video.seeking` の間は `currentTime` を代入できませんが、そこで指示を捨てると、シークの遅い側だけが止まったまま取り残されます（「片方の動画しか動かない」の原因）。`p.want` に覚えておき、`seeked` で追いつかせます。
- **モードは `App.registerMode(id, {...})` で登録します。** `players` / `zones()` / `onFile()` / `tabs` / `sMax()` / `timeFor()` / `readout()` を実装すれば、読み込み画面・タブ・操作バーは外枠が面倒を見ます。

## 動作を確かめたこと

自動テストで次を確認しています（Chromium、PC と iPhone のビューポート）。

- 水平速度の測定値が、合成動画の真の値（0.45 画面幅/秒）と一致
- 追いかけカメラで、飛行の終盤までボールが基準線の上に乗り続ける
- ミラー再生が最高点をはさんで対称（±43コマ）
- 同期再生のズレが、左右の開始点の差とコマ単位で一致
- ①→②の引き継ぎで、開始点が最高点のコマになっている
- `src/app.html`（分割）と `index.html`（結合）で結果が同じ
- スマホ幅で、ページ全体が縦にも横にもはみ出さず、映像 200px 以上・説明 110px 以上を確保
- ステップの前後移動、区間未設定のときに先へ進まないこと、「動画を変える」で読み込み画面に戻ること
- 3倍に拡大した状態でタップしても、取れる位置が等倍のときと一致すること
- ボタンを押しっぱなしにすると連続コマ送りになり、1回押しは1コマだけ進むこと
- 縦帯マスクの幅と濃さが変わること、並置中は同じコマを表示して片方だけカメラが動くこと
- 縦線の間隔がカメラの速さ×Δtになり、Δtを変えると表示も変わること
- 帯の位置がスライダー・タップ・ドラッグのどれでも動き、測定後は①の位置にそろうこと
- 中央の線が 100%／50%／0% で本当にその濃さになり、0% では画素として完全に消えること
- 帯のふちが「帯の外を隠す」由来で、それを 0% にすると消えること
- 中心の線の濃さと、帯の色の濃さがそれぞれ変わること
- 縦長・横長どちらの動画でも映像の枠が映像と同じ縦横比になり、**並べてもカメラの速度が変わらない**こと
- タップして位置を取るあいだはカメラのパンとマスクが止まり、タップ後に戻ること
- 「Δt すすむ／もどる」がちょうど Δt だけ動くこと、数値入力で 0.300 ちょうどになること
- カメラの速さが ±0.001 で動き、数値表示が3桁で追従すること
- ミラー再生のコマ送りが相対2コマ、「＋1コマ」で相対1コマ、「−1コマ」で相対3コマになること
- シーク中に来た指示が捨てられず、シーク完了後に指定の時刻へ追いつくこと
- ②で12コマ送ると左右**どちらも**12コマ進むこと、等倍と1/8の再生で**どちらも**進むこと
- 30 / 60 / 120 コマ/秒の動画をそれぞれ正しく実測し、そのあと1回押すとちょうど1コマ進むこと
- ステップを進めても戻っても、説明がいちばん上から始まること
- ボタンの上から始めたスクロールでは値が動かず、そのスクロール自体はちゃんと効くこと。タップは1回だけ、長押しは連打になること
- チェッカーが、一定間隔の動画を◎、間隔を間引いた動画を△、同じ画を水増しした動画を×と判定すること（小さく暗い物体でも同じ結果）
